\labpart{Краткое описание разработанного приложения}

В backend добавлен сервис \texttt{InMemoryRecordStore}, который хранит
записи в двух \texttt{ConcurrentDictionary}: отдельно конфиденциальные и
неконфиденциальные. Поверх него работают два контроллера с маршрутами
\texttt{/api/memory/confidential} и \texttt{/api/memory/public}
(создание, чтение, обновление, удаление, поиск). На фронтенде для них
добавлены две вкладки с тем же интерфейсом, что и у постоянных данных.

Конфиденциальные поля шифруются AES-256-GCM (класс
\texttt{ConfidentialCrypto} из лабораторной работы №2.1) в момент
создания или обновления записи, поэтому в словаре лежат только
зашифрованные байты (\autoref{lst:memstore}).

\begin{codelisting}[fontsize=\footnotesize]{csharp}{Создание конфиденциальной записи: шифрование до помещения в словарь}{memstore}
public ConfidentialEntry CreateConfidential(int ownerId, string title, string content)
{
    var id = Interlocked.Increment(ref _nextConfidentialId);
    var now = DateTime.UtcNow;
    var entry = new ConfidentialEntry(id, ownerId, Encrypt(title), Encrypt(content), now, now);
    _confidential[id] = entry;
    return entry;
}
\end{codelisting}

\labpart{Анализ защищённости приложения с точки зрения кода}

\begin{itemize}
  \item \textbf{Невалидные данные.} Размер и обязательность полей заданы
  атрибутами \texttt{DataAnnotations} в DTO (\texttt{Title} до 200
  символов, \texttt{Content} до 10\,000). Неверный тип поля,
  некорректный JSON, отсутствующее поле, пустое тело и слишком длинное
  значение приводят к ответу \texttt{400} без раскрытия внутренних
  деталей; проверка этих случаев приведена в части 2 лабораторной
  работы.
  \item \textbf{Конфиденциальные данные.} Данные шифруются сразу при
  вводе, ключ берётся из конфигурации, а не из кода. Промежуточные байтовые
  буферы в \texttt{ConfidentialCrypto} очищаются через
  \texttt{Array.Clear}. Строки \texttt{string} в .NET неизменяемы, поэтому
  очистить открытый текст, полученный из запроса, код приложения не может.
  \item \textbf{Параллельные запросы.} Используются
  \texttt{ConcurrentDictionary} и \texttt{Interlocked.Increment}, поэтому
  два запроса не получают один идентификатор.
\end{itemize}

\labpart{Анализ дампов оперативной памяти}

Дампы снимаются скриптом \texttt{dump\_analysis.sh}
(\autoref{lst:dump-script}) командой \texttt{dotnet-dump collect} после
создания, обновления и удаления двух записей. В каждой записи есть
уникальный маркер: \texttt{CONFIDENTIAL-MARKER-1} (после обновления --
\texttt{-2}) для конфиденциальной и \texttt{PUBLIC-MARKER-1} (после
обновления -- \texttt{-2}) для открытой. Дампы просматриваются в VS Code
в расширении Hex Editor, где маркер ищется как обычная строка.

\codelistingfile[fontsize=\footnotesize]{bash}{lab/code/dump_analysis.sh}{Скрипт снятия дампов}{dump-script}

Число найденных вхождений маркеров (\texttt{strings} в UTF-8 и UTF-16)
приведено в \autoref{lst:dump-counts}.

\codelistingfile[fontsize=\footnotesize]{text}{lab/code/dump_counts.txt}{Вхождения маркеров в дампах и их адреса в дампе после удаления}{dump-counts}

\begin{itemize}
  \item Маркеры обоих видов данных есть во всех трёх дампах, в том числе
  после удаления записи.
  \item Найденные копии -- это тело HTTP-запроса и ответа в формате JSON
  (в листинге видно строки вида
  \texttt{\{"title":"secret","content":"CONFIDENTIAL-MARKER-1"\}}), а не
  содержимое словарей приложения: там лежит только шифротекст.
  \item Конфиденциальный и открытый маркеры встречаются почти одинаково
  часто: шифрование защищает данные внутри хранилища, но не буферы,
  через которые данные приходят по сети и уходят обратно.
\end{itemize}

Вероятная причина -- переиспользуемые буферы, которые Kestrel и
\texttt{System.Text.Json} берут из общего пула и не обнуляют после
возврата. Эта гипотеза отдельно не проверялась. Скорее всего,
устранить эти копии кодом приложения нельзя.
