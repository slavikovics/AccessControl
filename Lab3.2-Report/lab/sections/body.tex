\labpart{Описание алгоритмов}

\textbf{Своя реализация (часть 1).} Раздел «In-memory data» приложения
\texttt{SecureApp}: ASP.NET Core, валидация через \texttt{DataAnnotations},
хранилище на \texttt{ConcurrentDictionary} с идентификаторами через
\texttt{Interlocked.Increment}, конфиденциальные поля шифруются
AES-256-GCM с ключом из конфигурации.

\textbf{Упрощённая реализация.} Консольная программа
\texttt{Lab3.2-NaiveVersion} на \texttt{HttpListener} с теми же
операциями (создание, обновление, удаление) без авторизации. Она
намеренно написана без учёта выводов части 1:

\begin{itemize}
  \item нет валидации: любая ошибка превращается в \texttt{500} с текстом
  исключения;
  \item нет ограничения размера запроса;
  \item «шифрование» -- XOR с ключом, записанным в коде
  (\autoref{lst:naive-xor});
  \item список \texttt{activityLog}, в который пишется открытый текст
  каждой операции и который никогда не очищается;
  \item обычный \texttt{Dictionary} и \texttt{nextConfId++} без
  синхронизации.
\end{itemize}

\labpart{Методика оценки безопасности кода}

Методика состоит из четырёх критериев. Каждый проверяется одинаково для
любой реализации и даёт результат «соответствует» или «не соответствует».

\begin{enumerate}
  \item \textbf{Невалидный ввод и размер данных.} Отправить семь
  запросов: неверные типы полей, сломанный JSON, пропущенное поле, пустое
  тело, 10\,050 символов, 5~МБ, переводы строки и табуляция внутри
  значения. Критерий выполнен, если каждая ошибка даёт конкретный
  код \texttt{4xx} без текста исключения, а слишком большие данные
  отклоняются.
  \item \textbf{Параллельный доступ.} Отправить 200 одновременных
  запросов на создание записи (по 50 одновременно). Критерий выполнен,
  если получено 200 уникальных идентификаторов, 200 записей сохранено, а
  чтение списка после этого работает.
  \item \textbf{Защита конфиденциальных данных.} По коду определить
  алгоритм и источник ключа. Критерий выполнен, если используется
  стойкий алгоритм с проверкой подлинности и случайным nonce, а ключ
  не хранится в исходном коде.
  \item \textbf{Конфиденциальные данные в памяти.} Снять дампы после
  создания, обновления и удаления записи с уникальным маркером и
  посчитать вхождения маркера. Критерий выполнен, если после удаления
  в дампе нет копий, оставленных кодом приложения (структуры данных,
  журналы). Копии, оставленные платформой, фиксируются отдельно.
\end{enumerate}

Корректность методики: проверки воспроизводимы (скрипты
\texttt{compare.sh} и \texttt{dump\_analysis.sh}), результат каждой
проверки -- число или код ответа, поэтому оценка не зависит от того, кто
её проводит. Методика различает реализации: на двух реализациях разного
качества она даёт разный результат (см. ниже), а критерии выведены из
реальных находок части 1 (валидация, шифрование, остатки данных в дампах).

\labpart{Анализ безопасности упрощённой реализации}

Проверки 1 и 2 выполнены скриптом \texttt{compare.sh}
(\autoref{lst:compare}) на свежезапущенных обеих реализациях.

\codelistingfile[fontsize=\footnotesize]{text}{lab/code/compare_output.txt}{Невалидный ввод и параллельный доступ: своя реализация (own) и упрощённая (naive)}{compare}

\begin{itemize}
  \item \textbf{Ввод.} Упрощённая реализация на четыре разных ошибки
  отвечает одинаковым \texttt{500} с текстом исключения, который раскрывает
  внутреннее устройство сервера. Данные в 10\,050 символов и 5~МБ она
  принимает без ограничений (\texttt{201}). Своя реализация возвращает
  \texttt{400} во всех этих случаях.
  \item \textbf{Параллельный доступ.} После 200 одновременных записей
  чтение списка в упрощённой реализации падает с \texttt{500}: два
  обычных словаря (заголовки и содержимое) рассинхронизировались.
  Состояние гонки недетерминировано: в другом прогоне два запроса
  получили один и тот же идентификатор, и одна запись была потеряна без
  ошибки. Своя реализация сохранила все 200 записей.
  \item \textbf{Шифрование.} XOR с постоянным ключом из кода
  обратим любым, у кого есть исходный код или исполняемый файл. Нет ни
  nonce (одинаковые данные дают одинаковый шифротекст), ни проверки
  подлинности.
  \item \textbf{Память.} Результаты дампов приведены в
  \autoref{lst:dump-counts-32}.
\end{itemize}

\codelistingfile[fontsize=\footnotesize]{text}{lab/code/dump_counts.txt}{Вхождения маркеров в дампах упрощённой реализации и строки журнала \texttt{activityLog} после удаления}{dump-counts-32}

После удаления записи число вхождений маркера в дампе не уменьшилось. Кроме
буферов запроса и ответа, как и у своей реализации, в дампе остались
строки \texttt{activityLog} с открытым текстом создания, обновления и
удаления записи. Это ошибка кода приложения, и она устранима: достаточно
не писать секреты в журнал.
